# 生命感知前端数据管线设计

## 目标

在现有三栏驾驶舱中接入可运行的生命感知逻辑，包括人员跟踪、生命体征处理、异常判定、实时波形和 CASE 生成。首个版本使用确定性的模拟串口数据，但模拟源必须输出与真实 TI mmWave 设备一致的二进制帧，使后续接入 Web Serial 时只替换字节来源，不重写协议解析、业务判定或界面。

## 范围

本次实现包括：

- 在浏览器 TypeScript 中解析 TI mmWave 标准帧和本功能需要的 TLV。
- 跟踪最多 2 名人员的位置、速度、高度、置信度和生命体征。
- 按参考程序处理心率中位数、生命体征波形窗口和跌倒判断。
- 自动运行一套可重复的双人模拟场景。
- 使用当前生命感知三栏布局展示雷达跟踪、指标、趋势、日志和 CASE。
- 保持中文、英文及现有主题支持。
- 隔离数据源，使模拟源可被未来 Web Serial 源替换。

本次不包括：

- 实际串口授权、端口选择、波特率配置或设备断线重连界面。
- 向雷达发送 `.cfg` 配置、CLI 指令或固件升级。
- Python 后端、桌面进程、WebSocket 中转或原参考程序的 PySide/OpenGL 界面。
- 摄像头画面、视频识别或基于图像的人员检测。

## 参考行为

设计以 `docs/reference_program/生命感知` 中的 TI mmWave 可视化器为依据，保留以下核心语义：

- 生命体征 TLV 类型为 `1040`，载荷格式为两个无符号 16 位整数和 33 个 32 位浮点数。
- 每条生命体征记录包含人员 ID、距离单元、呼吸偏差、心率、呼吸率、15 个心跳波形点和 15 个呼吸波形点。
- 压缩球坐标点云 TLV 类型为 `1020`，先给出 5 个浮点解压单位，再以 `2bh2H` 记录各点的俯仰角、方位角、多普勒、距离和信噪比。
- 3D 目标列表 TLV 类型为 `1010`，包含目标 ID、三维位置、三维速度、三维加速度和跟踪置信度。
- 目标高度 TLV 类型为 `1012`，包含目标 ID、最大高度和最小高度。
- 心率使用最近 10 次有效结果的中位数，避免瞬时抖动。
- 每名人员保留最近 150 个心跳和呼吸波形点。
- 呼吸偏差为 0 表示未检测到有效人员，低于 `0.02` 表示屏息。
- 跌倒判定比较当前高度与历史高度；当前高度低于 2.5 秒前高度的 60% 时进入跌倒状态。

参考程序中的 Python、NumPy、Qt 和 OpenGL 代码不会进入产品依赖。

## 总体架构

```text
[SimulatedSerialSource]                 [Future WebSerialSource]
             |                                   |
             +---------- Uint8Array chunks ------+
                                 |
                                 v
                    [MmWaveStreamDecoder]
                     framing + resync
                                 |
                                 v
                       [MmWaveTlvParser]
          point cloud + tracks + heights + vital signs
                                 |
                                 v
                    [LifeSensingAnalyzer]
              history + filtering + state rules
                                 |
                   +-------------+-------------+
                   |                           |
                   v                           v
          [LifeSensingCaseTracker]      [ViewModel Mapper]
                   |                           |
                   +-------------+-------------+
                                 |
                                 v
                    [LifeSensingDataProvider]
                                 |
                                 v
                       [React Dashboard]
```

图解：

- 这张图回答什么问题：说明模拟数据与未来真实串口数据如何共用同一条解析和业务处理路径。
- 节点/层级说明：数据源只负责产生字节；分帧器处理传输边界；TLV 解析器产生协议对象；分析器维护人员状态；Provider 管理生命周期并发布驾驶舱数据。
- 关键路径：有效字节从数据源进入分帧器，经协议解析和人员分析后，同时更新 CASE 与 Dashboard View Model。
- 分支/异常/变体：模拟源和 Web Serial 源是同一接口的两个适配器；坏帧在分帧器或解析器处丢弃，不进入业务状态机。
- 修改关注点：接入真实串口时只新增数据源适配器，不允许把串口 API、设备状态或二进制读取逻辑泄漏到 React 组件和分析器。

## 模块边界

新增 `src/lifeSensing` 目录，按责任拆分：

- `types.ts`：原始帧、TLV 结果、人员快照、状态、数据源和界面模型类型。
- `protocol.ts`：标准帧分包、魔数同步、帧头校验和 TLV 解析。
- `simulator.ts`：确定性场景、二进制帧编码和分块字节输出。
- `analyzer.ts`：每人历史、滤波、阈值、状态优先级和波形窗口。
- `caseTracker.ts`：异常进入、升级、恢复后的去重和 CASE 编号。
- `lifeSensingViewModel.ts`：领域快照到共享驾驶舱契约的映射。
- `lifeSensingDataProvider.ts`：组合数据源、解析器、分析器和 CASE 跟踪器，管理启动、停止、订阅和目标选择。

中央雷达画面由专用 `LifeSensingMedia` 组件渲染。共享 `DashboardShell` 只增加可选的生命感知控制接口，不承担领域计算。

## 数据源契约

数据源使用最小接口：

```ts
interface LifeSensingByteSource {
  readonly kind: 'simulated' | 'serial'
  start(sink: LifeSensingByteSink): Promise<void> | void
  stop(): Promise<void> | void
}

interface LifeSensingByteSink {
  onBytes(chunk: Uint8Array): void
  onStatus(status: 'connecting' | 'streaming' | 'stopped'): void
  onError(error: Error): void
}
```

`SimulatedSerialSource` 以约 10 Hz 输出数据，并故意使用变化的块大小拆分帧，以验证半包和粘包处理。未来的 `WebSerialSource` 只需把 `ReadableStream<Uint8Array>` 转发到同一 sink。

## 协议处理

`MmWaveStreamDecoder` 接受任意长度的 `Uint8Array`：

1. 将新字节追加到内部缓冲区。
2. 搜索 TI mmWave 魔数；丢弃魔数之前的噪声。
3. 缓冲不足一个标准帧头时等待后续字节。
4. 读取小端帧头中的总包长度、帧号、目标数量和 TLV 数量。
5. 拒绝小于帧头、超过配置上限或不是有效 32 字节填充长度的包。
6. 缓冲不足完整包时继续等待。
7. 解析已支持 TLV，跳过长度合法但类型未知的 TLV。
8. TLV 长度越界或载荷不完整时丢弃整个坏帧，并从下一个魔数恢复。

首个版本解析：

- `1020`：压缩球坐标点云，解压后转换为笛卡尔坐标供雷达视图使用。
- `1010`：3D 目标列表。
- `1012`：目标高度。
- `1040`：生命体征；同一标准帧中允许出现多条，解析结果按人员 ID 汇总。

所有数值使用 `DataView` 小端读取。解析器返回不可变的普通 TypeScript 数据，不依赖 DOM 或 React。

## 分析状态

每名人员按目标 ID 保存独立状态：

- 最近 10 个有效心率，用于中位数。
- 最近 150 个心跳波形点。
- 最近 150 个呼吸波形点。
- 最近 2.5 秒高度历史。
- 最近位置、速度和最后有效帧时间。
- 静止、屏息和生命体征异常的连续时长。

判定规则：

| 状态 | 进入条件 |
| --- | --- |
| `normal` | 人员有效，且无更高优先级异常 |
| `motionless` | 合速度低于 `0.03 m/s`，连续 5 秒 |
| `breathHold` | 呼吸偏差低于 `0.02`，连续 2 秒 |
| `vitalsAbnormal` | 心率低于 50 或高于 110 bpm，或呼吸率低于 10 或高于 24 bpm，连续 3 秒 |
| `fallen` | 当前高度低于 2.5 秒前有效高度的 60% |
| `notDetected` | 当前帧无此目标或呼吸偏差为 0 |

状态优先级为：`fallen > vitalsAbnormal > breathHold > motionless > normal`。`notDetected` 是数据可用性状态，不产生人员异常 CASE。人员重新出现时保留 ID 绑定，但连续计时重新开始。

## 模拟场景

模拟器每 36 秒循环一次：

| 时间 | 人员 1 | 人员 2 |
| --- | --- | --- |
| 0-6 秒 | 正常移动，生命体征稳定 | 正常移动，生命体征稳定 |
| 6-13 秒 | 逐渐停止并触发长时间静止 | 正常 |
| 13-19 秒 | 呼吸偏差下降并触发屏息 | 正常 |
| 19-27 秒 | 高度快速下降并伴随低心率，触发跌倒和生命体征异常 | 正常 |
| 27-36 秒 | 高度、运动和生命体征恢复 | 正常 |

位置、速度、波形和点云由固定公式与固定种子生成，测试和浏览器演示在相同时间点得到可重复结果。人员 2 使用不同轨迹和波形相位，验证数据不会串到人员 1。

## CASE 规则

- `motionless`、`breathHold` 和 `vitalsAbnormal` 生成警告 CASE。
- `fallen` 生成红色严重 CASE。
- 每名人员进入一个新异常或升级到更高优先级异常时生成一条记录。
- 同一异常持续期间不重复生成。
- 恢复正常后再次进入异常可生成新记录。
- 历史 CASE 最多保留 50 条，最新记录默认选中。
- `notDetected`、坏帧、数据中断和模拟器停止不生成人员异常 CASE。

## 驾驶舱行为

进入生命感知模块时，Provider 自动启动模拟源；离开模块或应用卸载时停止定时器、清空字节缓冲并取消订阅。重新进入时从确定性场景起点开始。

中央区域使用 SVG 绘制俯视雷达视图：

- 0-6 米距离网格和检测边界。
- 有上限的显示点云，避免真实设备高点数拖慢 React。
- 两名人员的当前位置、目标框、轨迹尾迹、目标 ID 和状态。
- 当前选中目标使用高亮样式；点击目标切换选择。
- 标题栏显示数据源为“模拟串口”及 `streaming/stale/error` 状态。

右侧 8 个指标沿用现有槽位，显示当前选中人员的前方距离、速度、楼层、点位、呼吸率、心率、生命状态和告警级别。趋势区域显示该人员最近 150 个呼吸和心跳原始波形点，纵轴为无量纲信号幅值；`bpm` 只出现在指标区，避免不同量纲共用坐标轴。

左侧厂区图、日志、CASE 表和处置面板保留现有布局。日志内容由真实状态转换产生，不再使用生命感知 Mock 异常数据。

## 错误与时效性

- 单个坏帧只增加解析错误计数，不清空最后一个有效画面。
- 连续 1 秒没有有效帧时状态变为 `stale`，界面显示“数据中断”。
- 数据恢复后自动回到 `streaming`，人员异常计时从新有效数据开始。
- 数据源抛错时状态变为 `error`，Provider 保持可停止和可重新启动。
- 解析错误、数据过期和数据源错误不得伪造人员异常 CASE。
- 组件卸载后到达的异步状态不得更新 React。

采用测试驱动实现，覆盖：

- `1040` 生命体征 TLV 的完整字段和 15+15 波形解析。
- `1020` 压缩点云的解压、符号位处理和球坐标转笛卡尔坐标。
- `1010` 目标列表和 `1012` 高度解析。
- 完整帧、半包、粘包、前置噪声、未知 TLV、坏长度和魔数恢复。
- 心率最近 10 次中位数和两组 150 点滑动窗口。
- 静止、屏息、生命体征异常和跌倒的边界与持续时间。
- 两名人员的历史、选择和状态隔离。

- 模拟源启停、确定性输出和 Provider 离开页面后的资源释放。

完整测试套件、TypeScript 检查、Vite 构建和 `git diff --check` 必须通过。Chrome 在 1600x900 下验证两名人员可见、点击切换正常、时间线能触发并恢复异常、CASE 不重复、中文与英文无重叠且控制台无错误。

## 真实串口升级路径

未来接入真实设备时：

1. 新增实现 `LifeSensingByteSource` 的 `WebSerialSource`。
2. 在用户手势中调用 `navigator.serial.requestPort()`，配置实际波特率并读取 `port.readable`。
3. 把读取的每个 `Uint8Array` 原样传给现有 sink。
4. 在标题栏增加数据源选择、连接和断开控制。
5. 使用记录的真实帧补充协议回归测试。

协议解析器、分析器、CASE 跟踪器、View Model 映射和雷达组件不因串口接入而改变。
